# reComputer RK3576 — JC-STAR の観点からの見立て（解説つき）

作成日: 2026-10-28 / 対象: Seeed Studio reComputer RK3576 / 段階: 実機未着・OSINTベース

> 「JC-STARって何？」から入り、その★1要件を“ものさし”にして、これまでのOSINT所見がどこを満たし／どこが実機待ち／どこは制度の対象外なのかを整理する。各項の `[Jn]` は §5 の一次ソース。

---

## 1. まずJC-STARとは（前提の解説）
**JC-STAR**（ジェイシースター、正式名：**セキュリティ要件適合評価及びラベリング制度** / Labeling Scheme based on Japan Cyber-Security Technical Assessment Requirements）は、**IPA（情報処理推進機構）が運営するIoT製品向けのセキュリティ・ラベル制度**。経産省の方針（2024年8月）を受けて整備され、**2025年3月25日に運用開始**（まず★1の申請受付）、初のラベル交付は2025年5月。取得は**任意**。[J1][J2]

ポイントを噛み砕くと:
- **「この製品は最低限のセキュリティ対策ができている」ことを、国の制度として星の数（★1〜★4）で示すラベル。** 食品の栄養表示みたいに、買う側が見分けやすくするための仕組み。
- **★の意味と評価方法:**
  | レベル | 想定用途 | 誰が評価するか |
  |---|---|---|
  | **★1** | 全製品共通の最低限要件 | **ベンダーの自己適合宣言**（自分で「満たしてます」と宣言） |
  | **★2** | 製品類型ごとの基本上乗せ | 自己適合宣言 |
  | **★3** | 政府・重要インフラ等での利用想定 | **第三者評価機関**での評価が必須・ラベル有効期間2年 |
  | **★4** | さらに重要なシステム向け | 第三者評価 |
  （通信機器向けの★3要件は2026年2月に公開された。）[J2][J3]
- **中身は国際規格と整合**: 英 **ETSI EN 303 645**、米 **NISTIR 8425**、英 **PSTI Act**、EU **CRA**、シンガポール **CLS**、**IEC 62443** 等にマッピングされている（★1要件書に対応表が載っている）。つまり「日本ローカルな独自基準」ではなく、世界の消費者IoTセキュリティ基準の共通項。[J4]

**重要な前提（誤解しやすい点）:**
- JC-STARは**“製品を作ったベンダーが申請して取るラベル”**。**買った人が自分の端末を「JC-STAR化」することはできない。** なので今回の使い方は「**★1の要件リストを、自分の点検の“中立なチェックリスト”として借りる**」というもの。
- JC-STARが見るのは**「実装されたセキュリティ衛生」**（初期パスワード、更新手段、不要ポート、通信保護など）。**半導体レベルのサプライチェーン信頼性や“どの国の企業の部品か”は評価対象外。** だから前回のQuectel（米NDAA 1260H）の論点は**JC-STARでは拾われない**＝別枠の話、という線引きが大事。

**この製品の現況:** reComputer RK3576 に**JC-STARラベルは付いていない**（初期の取得は富士ソフト等の国内製品。Seeedは申請していないと見られる）。だが★1要件を当てると、実装面の“素の体力”はかなり見える。[J2]

## 2. ★1要件（全16項目）に当てはめ
★1は `S1.1-01`〜`S1.1-16` の16項目。各項目はETSI EN 303 645 の条項にひも付く（下表の「ETSI」列は★1要件書の対応表から実抽出）。[J4]
**判定凡例:** ✅=OSINTで満たすと見える/設計上担保 ／ ◐=部分的・実機orベンダ文書で要確認 ／ ⬜=実機到着後に判定

| ★1項目 | ETSI | テーマ（平たく） | RK3576での見立て | 判定 |
|---|---|---|---|---|
| S1.1-01 | 5.1-3 | 初期パスワードが推測困難な生成か | Armbianは**万人共通の初期PWを持たず**、初回起動でユーザがPW設定する方式 | ✅ |
| S1.1-02 | 5.1-2 | PWが機器ごと一意 or ユーザ定義 | 同上（ユーザ定義パス）。[J6] | ✅ |
| S1.1-03 | 5.1-4 | 認証情報を変更できる | Linux標準で変更可 | ✅ |
| S1.1-04 | 5.1-5 | ブルートフォース耐性 | ボード定義のパッケージに **fail2ban** 同梱 [J7] | ✅ |
| S1.1-05 | 5.2-1 | 脆弱性の報告窓口がある | Armbianはセキュリティ報告プロセス有、Seeedも窓口有。ただし**製品としての脆弱性開示方針**は明文化を要確認 | ◐ |
| S1.1-06 | 5.3-1 | ソフト更新の手段がある | **署名付きapt更新**＋拡張リポに**A/B OTA**。更新手段は明確に存在 [J4][J5] | ✅ |
| S1.1-07 | 5.3-3 | 更新が容易/自動化可能 | apt/unattended、OTAで実現可 | ✅ |
| S1.1-08 | 5.3-7 | 更新の真正性・完全性の検証 | **apt=PGP署名検証**、イメージ=`.asc`署名、セキュアブート有 [J4] | ✅ |
| S1.1-09 | 5.3-8 | 更新配信の安全な通信 | 配信はHTTPS＋署名 | ✅ |
| S1.1-10 | 5.3-16 | サポート期間の明示 | Armbianの保守状況は公開。**製品としての明示サポート期限**はベンダ確認 | ◐ |
| S1.1-11 | 5.4-1 | 重要パラメータの安全な保管 | 拡張リポに **LUKS自動アンロック(OP-TEE)**・セキュアブート。既定イメージでの有効化は実機確認 | ◐ |
| S1.1-12 | 5.5-1 | 通信の保護（適切な暗号） | 配布=HTTPS/PGP、遠隔操作=SSH。実運用の通信は実機で | ✅ |
| S1.1-13 | 5.6-1 | **不要な攻撃面の最小化** | **本調査の主戦場**。conf上、既定でFastboot無効・USBガジェット(ttyGS0 getty, usb0=192.168.42.1)が既定攻撃面として判明。開放ポート/常駐は**実機で `ss`/`systemctl`** | ◐ |
| S1.1-14 | 5.9-1 | 障害・停電への耐性 | A/B OTAでロールバック耐性 | ✅ |
| S1.1-15 | 5.11-1 | 利用者データの削除容易性 | 再フラッシュ/MaskROMで初期化可（開発ボード性質上、消費者データ概念は薄い） | ◐ |
| S1.1-16 | 5.12-2 | 設置・保守の手引き提供 | **Seeed Wiki＋Armbian公式**で手順充実 [J1][J6] | ✅ |

### 当てはめの要約
- **設計・配布まわり（PW・更新・通信・署名）は★1水準を実装面で満たすと見てよい。** Armbian＋署名付きapt＋OTA＋fail2anという素性が効いている。
- **◐（要実機/要文書）の中心は2つ:** ①S1.1-13（**不要ポート/サービスの最小化**＝まさにバックドア調査でやる `ss -tulpn`/`systemctl` の確認）、②S1.1-05/-10（**脆弱性開示方針・サポート期限**というベンダのプロセス文書）。
- どれも**自己適合宣言★1なら“満たせる土台はある”**。実機到着後のポート確認でS1.1-13が埋まれば、★1相当のチェックは実務上ほぼ通る見立て。

## 3. ★2〜★4に上げると何が増えるか（参考）
- **★2**: 製品類型（例：通信機器）ごとの上乗せ要件。ルータ類ならファイアウォール既定・ログ等が足される。これも自己宣言。
- **★3/★4**: **第三者評価機関**による評価が必須。設計書・脅威分析・ペネトレーション結果等の提出を伴い、個人購入者の点検の範囲を超える（＝ベンダー側の取り組み）。今回の“到着前OSINT＋到着後の軽装備点検”は**★1の自己点検レンジ**に対応、と理解するのが正確。[J3]

## 4. JC-STARと「バックドア調査」の関係整理（線引き）
- **重なる部分:** 不要な通信/ポート最小化(S1.1-13)、更新の真正性(S1.1-08)、通信保護(S1.1-12)は、バックドア調査でも核心。JC-STAR★1は**“実装衛生の抜け”を体系的に見るチェックリスト**として有用。
- **JC-STARでは拾えない部分（別枠）:**
  - **SoC内BootROM/OTP/クローズドブロブの内部**（原理的に検証不能＝制度も踏み込まない）。
  - **部品のサプライチェーン地政学**（Quectelの米NDAA 1260H掲載など）。JC-STARは“どの国の企業の部品か”を評価しない。→ この観点は**JC-STARの外**に置き、前回レポート §5 の扱いのまま残す。
- つまり: **JC-STAR★1 = 「作り手がちゃんと基本衛生を実装したか」の物差し**。今回の調査 = 「出荷個体に作為が無いか＋サプライ網の透明性」。**両者は補完関係**で、片方がもう片方を代替しない。
